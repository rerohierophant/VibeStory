状态（2026-11-05）：**当前原型范围已完成，包含阶段一至十三**。最新独立 PostgreSQL 16 数据库模式全套 Mock 回归通过：189 项后端、17 项组件、17 项 Chrome，以及类型检查、契约生成、前端构建与真实 HTTP 续约 / SIGKILL / 重启回归，详见[最新验收](image-learning.md#2026-11-05-验收结果)。阶段七、八的真实 RabbitMQ / Redis 专项与故障验收单列，不计入本次数据库模式回归。历史真实供应商验证不因这些 Mock 测试扩大；本轮无真实模型调用，用户已取消录屏。真实 Homebrew PostgreSQL 16 / RabbitMQ 4.4.0 / Redis 8.10.3，Docker / Testcontainers 启动分支未运行。各阶段记录保留原始验收数量与证据。

**阶段七已实现**：整集批次、事务 Outbox、RabbitMQ 4.4.0、独立 / 双 Worker、批量页面和持久化派发指标；记录见 [阶段七](backend-phase7.md)。**阶段八已实现**：Redis 统一多个 Worker 共用凭证的新生成提交速率，17 项真实 Redis 专项与双 JVM / 故障 / 页面验收通过，见 [阶段八](backend-phase8.md)。协议见 [技术方案 §19、§20](tech-design.md)。

本版路线已按页面结构重排：**集是生产单位**，所以「分集」从阶段二就出现，而不是等到镜头阶段才补一个字段。导出、用量、手工补镜、拖拽排序不在本路线中；阶段七的「本集批量生成」已同步实现页面与接口，提供逐镜接收 / 复用 / 阻塞结果及刷新恢复。

## 排序原则

不按日历排期，按**依赖关系**排序：

1. **先通一条链路，再往两侧扩。** 任何一个阶段结束时，从浏览器点得通、看得见。
2. **每一步的产物是下一步的输入。** 上一步没有的东西，不在下一步补。
3. **页面已经给出的交互，后端必须能承载。** 不允许出现「页面能点、后端没接口」的悬空状态。
4. **先完成 RabbitMQ 任务分发，再做 Redis 共享限流。** 阶段七先用本地执行槽位验证独立 / 多 Worker；阶段八再解决共享模型额度，不能用 Redis 替代任务表、幂等或租约。

标记说明：**[必做]** 缺失即链路不通；**[推荐]** 显著提升完成度，时间允许就做；**[可选]** 有余力再做，砍掉不影响演示。

阶段七、八的 **[必做]** 是各自阶段的完成条件，不反向改变阶段一至六的已验收结论。后续验收全部使用 Mock / 本机 HTTP fixture，不再提交真实图片或视频生成；真实中间件验证与仅适配器单测分开记录。

## 阶段一：后端骨架与最小纵向链路

**已完成**：19 项自动化测试通过；HTTP 并发提交、续约、SIGKILL 后重启恢复、跨用户 404 验收通过。本机没有 Docker，自动化测试使用显式指定的 Homebrew PostgreSQL 16；默认 Testcontainers 路径已提供但尚未执行。

**为什么排第一**：状态机、任务表、幂等这三件事决定了后面所有交互形态。先在前端之前定下来，后面改的是 UI，不是数据模型。

### 1.1 工程骨架 **[必做]**

- JDK 21 已安装，初始化 Spring Boot 3 + Gradle 工程；`scripts/java21.sh` 显式选用 21。
- Flyway 迁移 `V1__init.sql`：`app_user`、`project`，以及本阶段依赖的最小 `episode`、`shot`、`shot_image`。这些前置表不代表第二、三阶段完整业务已完成。
- 统一错误响应（ProblemDetail）、参数校验、springdoc OpenAPI 可访问。
- 本地 `docker-compose.yml`：PostgreSQL 16；`application-local.yml` 与 `.env.example`。集成测试用 Testcontainers 起真实 PostgreSQL，不用 H2。

### 1.2 账号与作用域 **[必做]**

- 登录 / 登出 / `GET /api/me`；BCrypt 存密码；注册接口留作种子数据，不对外暴露页面。
- `ScopeGuard`：`userId → projectId → episodeId → shotId` 逐层校验，越权返回 404。
- 一条集成测试：A 访问 B 的项目返回 404。

### 1.3 任务机制 **[必做]**

- `V2__task.sql`：`task`、`task_attempt`、成功视频结果 `video`，含活跃任务部分唯一索引与 `episode_id`。
- 租约轮询 Worker：`FOR UPDATE SKIP LOCKED` 领取、90 秒租约、30 秒续约、乐观锁。
- `input_signature` 规范化函数 + 单元测试（空格、换行、key 顺序、浮点精度、nonce）。
- `MockVideoProvider`：固定 3 秒占位视频，可配置延迟与失败率。

### 1.4 最小全链路 **[必做]**

- `POST /api/projects` → `POST /api/projects/{id}/episodes` → `POST /api/shots/{id}/video-tasks`（先用手工插入的占位镜头）→ Worker 执行 → `GET /api/tasks/{id}`。
- 不碰前端，用 `scripts/verify-phase1.py` 走真实 HTTP；占位镜头与逻辑首帧由 `scripts/fixtures/phase1-shot.sql` 插入。

**阶段验收**

- 全链路可跑通，任务状态按 `QUEUED → RUNNING → SUCCEEDED` 流转，API 投影为「产物就绪」。
- Worker 中途被杀，租约到期后任务被重新领取，`attempt` 递增。
- 同一输入连续提交 10 次，只有一条活跃任务、一条进行中尝试。
- 跨用户访问返回 404。

**刻意不做**：前端联调、真实供应商、资产、Agent。

## 阶段二：项目、分集与故事

**已完成**：阶段二 17 项新增集成测试通过，连同阶段一共 36 项测试通过。真实 HTTP 验证了自定义图上传、三集正文与风格在 JVM 重启后恢复、越权 404、删除中间集保留序号及媒体清理。前端仍为本地状态，完整联调留到阶段六。

**为什么是第二**：集是后面所有产物的容器。先让「项目 → 分集 → 正文」这条骨架可持久化，拆解与生成才有地方落。

### 2.1 项目 **[必做]**

- `project`：名称、画面风格的稳定字符串 ID（`visual_type`）、可选风格描述；分类和标签从风格目录解析，不限定为固定数量的枚举。具体字段契约见 product.md「画面风格契约」与 tech-design.md §3.6。
- 承载页面已有的四类选择与自定义风格：内置目录保持现有 ID；自定义条目持久化 ID、用户归属、名称及参考图存储引用，提供列表、新增与删除能力。项目保存所选条目 ID，引用自定义条目时校验用户归属。
- 已实现内置目录同步与私有 JPEG / PNG 参考图；删除自定义条目将其移出选择器，已有项目继续保留引用，最后一个项目解除引用后清理图片。
- 列表、搜索、新建、重命名、删除；当前删除级联清理分集、镜头、图、视频及任务，媒体通过持久化清理记录最终删除。后续资产表实现时也须接入级联清理。
- 概览统计接口：分集数、镜头数、已确认数、已选定分镜图数、已出片数。

### 2.2 分集 **[必做]**

- 在阶段一 `episode` 表与创建接口上补齐分集业务；后续结构变化新增迁移，不修改已经执行的 `V1/V2`。
- 新建一集（`index` 取当前最大 + 1）、改集名、改梗概。
- 为删除中间集的阶段验收提供删除接口；删除后不重排剩余集号，尚不增加前端入口。
- 集内统计：镜头数、已确认、有图、有视频。

### 2.3 正文 **[必做]**

- `PUT /api/episodes/{id}/story`：整体替换正文，保留唯一原文。
- 大小与编码校验；`.txt` / `.md` 由前端读取后按文本提交，后端不解析文件。
- 修改正文把 `breakdown_state` 从 `DONE` 回退为 `IDLE`，但不删镜头。

**阶段验收**

- 建项目 → 建三集 → 每集各写一段正文 → 刷新后完整可读。
- 内置预设与自定义参考图都能用于建项目；刷新后选定的风格、名称和参考图可恢复，跨用户不可引用他人的自定义风格。
- 连续新建时 `index` 连续且唯一；删除中间一集后允许缺号，其余集的 `index` 不变，新集取当前最大值 + 1。
- 跨用户访问集与正文返回 404。

**刻意不做**：拆解、资产、生成。

## 阶段三：拆解与镜头清单

**已完成**：拆解、镜头编辑与确认、名称解析及 OpenAI-compatible 文本适配器。真实 DeepSeek 业务链路以 1 次尝试将 850 字符剧本拆为 36 镜；Mock HTTP 链路为 20 镜，编辑与确认状态均通过两次 JVM 重启验收。已有前端覆盖弹窗未改动；后端以 `replaceExisting` 校验确认，前端仍未联调。自动化与证据边界见 [backend-phase3.md](backend-phase3.md)。

**为什么是第三**：正文必须变成结构，后面所有生成才有依附对象。这是第一个「AI 真的在工作」的地方。

### 3.1 镜头模型 **[必做]**

- 在阶段一最小 `shot` 表上补齐镜头业务；沿用 `(episode_id, seq)` 唯一约束，需要扩表时新增迁移。
- 状态机：`DRAFT ⇄ CONFIRMED`，取消确认是对外接口。
- `DRAFT` 提交生成返回 409；`CONFIRMED` 仍可改字段、切图、重做视频，不设额外写保护。

### 3.2 拆解任务 **[必做]**

- `TextProvider` 接口 + `MockTextProvider`：把前端 `lib/splitter.ts` 的规则原样移植（按空行分段、句末切分、引出语并句、场景词表匹配、台词判断景别），保证同一正文拆出同一结果。
- 拆解结果写入镜头，标记 `DRAFT`；同一份正文重复触发复用未完成任务。
- 重新拆解在同一事务内清空该集旧镜头与媒体，任务与尝试保留。
- 输入保存提交时正文、模型与场景目录快照，以及正文 / 镜头修订号；等待期间正文或镜头被改动，旧结果不应用。成功替换时取消旧镜头的活跃生成任务，阻止其晚到结果写回；人物与场景卡保留。
- 对齐已实现的前端保护：首次拆解直接提交；已有镜头时弹出覆盖确认，取消不提交，确认后才启动拆解，执行中禁用按钮。

### 3.3 镜头编辑与确认 **[必做]**

- `PATCH /api/shots/{id}`：描述、台词、景别、运镜、场景名、时长。
- 单镜确认 / 取消确认、整集确认。
- 编辑结果刷新不丢。

### 3.4 资产名称解析 **[必做]**

- 拆解产出的 `scene_name` / `character_names` 按项目内名称解析为资产，未命中则建卡。
- 名称在项目内唯一（`lower(name)`），重复只建一张卡。

### 3.5 真实文本模型接入 **[推荐]**

- 一个真实 `TextProvider` 实现，输出严格的 JSON 结构，解析失败要能看出原始响应。
- 通过配置开关切换，默认仍是 Mock。
- 默认干净环境为 Mock；本机忽略配置按用户要求选用 `https://api.deepseek.com` / `deepseek-flash`。真实文本超时或租约丢失进入 UNKNOWN，不自动重放；诊断接口可读取脱敏的原始响应。

**阶段验收**

- 一段 800 字正文拆出 ≥10 个可编辑镜头。
- 同一正文重复触发拆解，不产生第二条活跃任务；重新拆解后旧镜头被清理。
- 已有镜头时，打开并取消重新拆解弹窗不改变镜头、确认状态或生成结果；确认后只重建当前集镜头，当前剧本、人物库和场景库保留。
- 未确认镜头无法提交生成，且接口返回 409 而不是静默忽略。
- 已确认镜头改字段成功；取消确认后回到待确认，仍不可提交生成。
- 拆解出的角色名只建一张卡。

**刻意不做**：新增分镜图 / 真实视频供应商、资产版本；沿用阶段一 Mock 视频作为回归链路。

## 阶段四：资产库与分镜图

**已完成**：资产上传 / 生成版本、基准选择、项目 / 全局库与使用统计、图片任务、不可变来源快照、候选选择及按集状态投影。MiniMax `image-01` 只做了一次真实文生图，1 个 attempt、1 张 1280×720 JPEG；其单人物参考图协议由本机 fixture 验证。Mock HTTP 在两次 JVM 重启后保留图片、来源和选择；前端数据层在第五阶段后完成联调。详细边界见 [backend-phase4.md](backend-phase4.md)。

**为什么是第四**：有了镜头才有「引用谁」的问题；资产版本和引用快照必须在第一次生成之前就位，否则一致性设计无从谈起。

### 4.1 资产模型 **[必做]**

- 在 V4 已有 `character_asset`、`scene_asset`、`asset_ref` 名称卡基础上新增资产版本迁移与选中版本约束；不重建这些表。
- 资产只包含人物与场景；`shot_image` 是镜头的生成产物，不纳入资产库。
- 版本来源分 `uploaded` / `generated`；同一资产只能有一个 `is_selected`。

### 4.2 资产接口 **[必做]**

- 项目内角色库 / 场景库列表；全局资产库（跨项目）列表，带项目名与使用统计。
- 新增版本（生成 / 上传）、切换选定版本。
- 使用统计：出现于多少个镜头、哪些集；按名称聚合，与页面展示一致。

### 4.3 分镜图生成 **[必做]**

- 新增迁移扩展已有 `shot_image` 的标签、任务关联与图任务处理；沿用已存在的选中约束与来源字段，不重建该表。
- `ImageProvider` + `MockImageProvider`：按 `input_signature` 生成确定性占位图。
- 提交生成时固定引用的人物 / 场景当前选定版本，持久化输入快照；Worker 使用该快照，完成后写入每张候选图的 `input_snapshot`，不在完成时读取最新基准版本。
- 预览与编辑抽屉展示人物 / 场景的资产名称、版本展示名；响应保留资产 ID、版本 ID。分镜图不设 `stale` / `stale_reason`，换基准版本不使已有图失效。
- 第一张 `READY` 自动 `selected`；已确认镜头同样可以切图。

### 4.4 分镜接口与轮询 **[必做]**

- `GET /api/episodes/{id}/shots?filter=all|todo|draft`：一次返回该集镜头、候选及生成来源、视频摘要。
- `GET /api/episodes/{id}/shots?taskActive=true`：按集轮询的收敛点，3 秒一次，页面失焦停止。
- 响应形状直接对齐 `types.ts` 的 `Shot`，减少前端改造。

### 4.5 真实文生图接入 **[推荐]**

- 一个真实 `ImageProvider`，支持参考图输入；能力不足时降级为纯文生图并在 UI 标注。

**阶段验收**

- 生成分镜图时确实带上引用的资产版本（可从 `input_snapshot` 断言）。
- 换人物或场景基准版本后，已有分镜图仍可使用，原来源快照不变；新提交的生成使用新版本。生成期间换基准版本，本次结果仍记录提交时的版本。
- 历史图来源缺失时显示「未记录」，未关联的引用不伪造版本；页面没有分镜图陈旧徽标或强制重做提示。
- 单镜重生成不影响其他镜头；第一张图自动选定，后续候选可手动切换。
- 同一镜头同一输入重复提交复用未完成任务；点「再生成一版」产生新任务。

## 阶段五：图生视频与首帧来源

**已完成**：MiniMax Hailuo 2.3 Fast 的图生视频、首帧冻结、供应商任务号持久化与恢复查询、手动重试 / UNKNOWN 区分、真实播放器、MP4 校验和实际时长。唯一一次真实生成输出 1364×768 / 5.875 秒；另有一次调用前的本地配置拒绝，两者均保留审计。详细过程与验证边界见 [第五阶段](backend-phase5.md)。

**为什么是第五**：视频以分镜图为输入，需要先具备可选的首帧和可追溯的生成来源。

### 5.1 视频生成 **[必做]**

- `video(shot_id, source_image_id, source_image_version, status, attempt_count, error_message)`。
- 以提交时选定的分镜图为首帧；Worker 记录提交时的首帧，而不是结束时的最新图。
- 播放、失败原因、重试；`attempt_count` 与 `task_attempt` 对账。

### 5.2 首帧来源追溯 **[必做]**

- `source_image_id` / `source_image_version` 在提交时固定；生成期间切图不改变本次视频的输入。
- 切换当前分镜图不改写已有视频、不取消已生成状态；卡片和预览按视频记录的首帧展示。
- 视频页保留首帧来源，缺失时显示「未记录」；已有视频继续可用，用户按需重新生成。

### 5.3 视频接口 **[必做]**

- `GET /api/episodes/{id}/shots` 的视频摘要字段满足四种筛选：全部 / 已生成 / 未生成 / 失败。
- 只返回已确认镜头的出片能力；未确认或未选图时接口拒绝并给出可读原因。
- 失败与「结果未知」分开：可重试的失败允许重试；未知要求用户显式确认。

### 5.4 四种提交情况 **[必做]**

- 重复提交复用任务；主动重新生成走 `regenerate_nonce`；可重试失败新建 attempt；外部结果未知置 `UNKNOWN` 并交给用户决策。

### 5.5 批量操作 **[推荐]**

- 整集确认已有页面入口，必须落到接口；逐条走状态机，不允许绕过。

**阶段验收**

- 连续点提交只产出一段视频。
- 失败后可重试，attempt 记录清晰，页面「尝试 N 次」与后端一致。
- 生成期间或完成后切图，已有视频仍计入已生成；刷新后首帧来源保持不变。
- 供应商超时不会被误判为成功，页面显示「结果未知」。

## 阶段七：RabbitMQ 与整集批量任务分发（已实现）

**业务场景**：创作者在一集内批量提交已确认镜头的分镜图或视频生成，API 返回批次后即可离开页面；独立 Worker 按文本 / 图片 / 视频通道消费，两个 Worker 可以协作执行。数据库继续保存任务事实、来源快照、幂等和租约。设计细节见 tech-design §19。

**前置条件与顺序**：阶段一至六基线通过 → 批次契约与 Outbox → RabbitMQ 投递 → 独立 Worker 消费 / 恢复 → 新页面入口与故障验收。本阶段不依赖 Redis，沿用每进程执行槽位。

### 7.1 批次模型与提交契约 **[必做]**

- 新增批次及成员记录，关联用户 / 项目 / 集、稳定请求幂等键、逐镜接收 / 复用 / 阻塞结果与 task ID。重复同请求复用批次，同键不同内容拒绝；主动重新生成使用新键 / nonce。
- 批量提交复用单镜业务服务，逐镜校验作用域、确认状态、首帧及活跃任务。阻塞成员记录原因，不创建任务；合格成员的任务、批次成员和 Outbox 在同一事务提交，数据库失败整体回滚。
- 图片与视频分开提交，不自动确认镜头、自动选择首帧或连跑跨集流程。提交时固定输入与版本，换基准图或切图不改写历史产物。
- 已提供批次提交 / 查询契约及按成员聚合的进度，越权返回 404；页面与 springdoc 0.7.0 生成类型同步更新。

### 7.2 Outbox 与 RabbitMQ 投递 **[必做]**

- 新迁移增加 Outbox、任务派发轮次、`not_before` 与投递状态 / 索引；不修改已执行迁移。Outbox 与任务状态变化同事务，`(task_id, dispatch_generation)` 唯一。
- Relay 带短租约领取到期事件，使用持久化消息、publisher confirms 与 mandatory return 检查；仅确认且正确路由后标记已发送。发布后崩溃允许重投，不能假设一次发送即只消费一次。
- 配置文本 / 图片 / 视频持久化队列与死信队列；Mock 验收使用独立命名空间并继续校验 provider。消息只传身份与契约版本，凭证、正文及媒体不进入 MQ。
- 有界退避由 Outbox 到期时间驱动；不无限立即 requeue。毒消息进入死信；有效任务记录派发阻塞并暂停自动重派，修复后显式恢复，不能无限复活。

### 7.3 独立 Worker 与领取恢复 **[必做]**

- 同一代码库支持 API / Worker 运行角色；API 不执行媒体任务。本机多进程共享 PostgreSQL 与同一本地媒体根目录，不拆领域微服务。
- 消费者受本地执行槽位约束，按消息指定 task / 派发轮次事务领取；领取成功提交后手动 ACK，长任务交给现有执行服务。`prefetch` 与在跑任务并发分别配置。
- 旧轮次、有效租约内重复通知、已终态与已删除资源不重复执行；不把数据库故障当作资源已删除。数据库派发和 MQ 派发模式互斥。
- 协调器处理到期排队任务与过期租约：等待超时的排队通知复用当前轮次 Outbox 重投，新恢复轮次才轮转身份；已有待投递 / 未超时通知时不反复作废旧消息。ACK 后崩溃、消息异常丢失不能使任务永久搁置，owner / version fencing 继续拒绝过期 Worker 写回。
- 已有 external ID 的视频接续原 attempt 查询 / 下载；Mock 可安全重放；真实请求结果未知继续按 `UNKNOWN` 处理，不能通过消息重投自动重新生成。

### 7.4 页面、观测与本地启动 **[必做]**

- 在分镜 / 视频页新增「本集批量生成」入口，展示成员选择、前置校验与接收 / 复用 / 阻塞结果；批次状态可在刷新后恢复，单镜操作继续可用。
- 增加 Outbox 等待、投递重试、重复通知、死信、各类型排队 / 执行与租约恢复的观测，不预设吞吐提升指标。
- 已新增 RabbitMQ 4.4.0 的依赖、本地启动配置与运行角色，使用单节点；保留数据库模式全 Mock 回归入口。

**阶段验收（已执行，实际环境与注入方式见 [阶段七记录](backend-phase7.md)）**

- 用真实 PostgreSQL + RabbitMQ 与 Mock Provider 跑通页面批量提交 → 批次返回 → 两 Worker 执行 → 刷新查询结果；同时覆盖单镜回归、类型通道隔离与跨用户 404。
- 并发重复批次提交与重复消息只产生一次预期业务执行；主动重生成有独立任务身份；生成期间换基准版本 / 首帧，产物仍记录原输入。
- 注入事务回滚、MQ 断线 / 重启、确认丢失、发布后未记发送、领取后未 ACK，以及 ACK 后 Worker 被杀；分别证明不产生孤立提交、可重投、可接管且旧 Worker 写回被拒绝。
- 数据库 / 路由错误有界重试或进入死信；任务可查询，毒消息不会被协调器无限重派，显式修复后可继续；`UNKNOWN` 不被自动重放。
- 用本机 HTTP fixture 验证已有外部任务号恢复只查询 / 下载，复用原 attempt。Mock-only 防线继续阻止真实供应商调用。
- 记录实际使用的 RabbitMQ 版本、运行方式、故障样本与结果；未执行的 Docker / Testcontainers 路径不能计为已测。

**范围边界**：不引入 Redis、MQ 集群、服务注册中心、微服务拆分、跨集 DAG 或 Agent Runtime；不承诺外部 exactly-once。

## 阶段八：Redis 多 Worker 共享生成提交限流（已实现）

**业务场景**：阶段七的两个及以上 Worker 共用同一模型凭证时，单进程限流会叠加。Redis 负责统一新生成提交的速率和突发量；任务排队、结果、幂等和租约仍由数据库负责。设计细节见 tech-design §20。

**前置条件与顺序**：先完成阶段七的批量生成、两 Worker 消费与崩溃验收，再接 Redis；先定义共享额度分组，再接执行准入、故障处理和多 Worker 验证。

### 8.1 共享额度与原子准入 **[必做]**

- 采用令牌桶，服务端配置 `rate` / `burst`，Redis Lua 原子补充、检查与扣减，使用 Redis 时间，返回允许结果及 `retryAfterMs`。
- 按供应商、接口和不透明共享凭证配置 ID 分桶，同凭证跨 Worker / 用户 / 配置别名共享；MiniMax 图片 / 视频共用提交总桶，DeepSeek 使用独立桶，本期不扩展子桶或配额树。key 和日志不包含密钥或正文。
- TTL 至少覆盖空桶补满时间并留余量；演示参数可配置，不把它写成供应商真实限额。
- 明确区分共享提交速率和单 Worker 在跑数量；本阶段不增加全局在途并发许可证、用户每日配额或计费系统。

### 8.2 接入 Worker 与延迟派发 **[必做]**

- 新生成在数据库正式领取 / 创建 attempt 之前申请额度；Redis 调用不持有数据库行锁。先校验任务有效并取得本地槽位，再申请令牌，成功后条件领取。
- 额度不足时，条件更新任务的 `not_before` / 等待原因，轮转派发身份并写入到期 Outbox，保持 `QUEUED`；释放槽位、ACK 当前通知，等待到期派发。不新增 attempt，不记生成失败，不立即热重投。
- 准入后领取竞态失败可保守消耗令牌，不自动返还；任务执行所有权仍以数据库为准。业务重试 / 主动重生成重新申请，外部任务号恢复只继续查询 / 下载。
- 所有生成提交入口复用执行服务；未来 CLI / MCP 使用同一机制。查询与下载沿用原有间隔 / 超时，本阶段不宣称限制全部供应商 HTTP 请求的 QPS。
- 许可只用于随后一次提交，超出短有效期须重新申请；已领取时保留原 attempt 并续约，不无许可调用。分别记录原子准入与请求发起时刻，区分应用准入速率和供应商端受网络影响的到达速率。

### 8.3 不可用策略与观测 **[必做]**

- Redis 超时 / 断线 / 脚本失败时暂停新生成提交，任务保持排队并退避；不退回各进程独立限流或无限制执行。已有远程任务查询 / 下载、租约续约与结果落库继续。
- Redis 重启 / 状态丢失后，由数据库锁下的单一协调者推进持久化恢复代次，所有 Worker 对齐，再将受影响桶从零令牌重建后补充，不允许各进程自行获得满桶突发量。
- 增加准入允许 / 拒绝 / Redis 错误次数、等待时长及实际提交计数；沿用数据库中的任务状态展示。已增加 Spring Data Redis、Lua、配置与单节点 Redis 启动项。

**阶段验收（已执行；实际证据见 [阶段八记录](backend-phase8.md)）**

- 使用真实 PostgreSQL + RabbitMQ + Redis，启动至少两个独立 Worker 竞争同一凭证桶；所有生成使用 Mock / 本机 fixture。按原子准入时间和令牌桶 `burst + rate × 时间区间` 上界验证共享额度，允许少量保守少发，不允许按进程倍增。
- 验证同凭证跨类型 / 配置别名共享、不同凭证隔离、空闲过期重建与领取竞态；排队限流不创建 attempt，许可过期等待不重复创建 attempt，重复通知和延迟派发不造成多次提交。
- 用独立探测器 / Mock 服务日志核对实际请求身份、次数与准入到调用延迟，并注入许可过期，避免只断言 Redis 计数；不将本地限流断言冒充供应商端任意窗口的精确 QPS 保证。错误、拒绝与等待不混入生成失败率。
- 注入 Redis 不可用 / 恢复与 Worker 重启：新任务排队、无无限制降级，已有任务仍可收尾；恢复后统一重建并逐步放行，无额外突发。现有外部 ID 不被重交。
- 验证 key、消息和日志不含密钥；第七阶段的死信、幂等、崩溃恢复和作用域回归仍通过。分别记录真实中间件验收与仅算法单测，不新增真实图片 / 视频生成。

**范围边界**：不增加 Redis 缓存、分布式任务锁、Redis 队列、Sentinel / Cluster、计费 / 每日配额、跨供应商自动切换或真实吞吐承诺。

个人项目的分镜与人物 / 场景图支持按原结果纠正、比较候选并明确评价。满意的做法可编辑后保存为素材、项目或个人范围的偏好，后续同类出图自动参考。创作配方支持文字槽位、跨项目素材绑定与不可变版本，任务冻结实际使用的偏好和配方。页面与 Agent 共用受控服务，使用方式和验证入口见[图片学习说明](image-learning.md)。

## 不做（本版本）

成片剪辑、调色、混音、字幕轨、数字人、多集串行批量生产、实时多人编辑与细粒度项目授权、模板化批量投放、移动端、计费与支付。

以及**页面没有入口、因此本期不进后端**的四项：

- 镜头的手工补镜、删除、拖拽排序。
- 分镜包导出。
- 用量 / 费用统计与每日额度。
- 项目封面图上传（当前显示独立的项目占位图，不使用风格参考图）。

判断一个需求该不该做，用一句话：它是否服务于「任务状态机、幂等、作用域隔离、版本与来源追溯」。不服务于这四件事、页面又没有入口的产品功能，一律不做。
