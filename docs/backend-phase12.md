# 阶段十二 · 分集 Agent 工作流

## 三层渐进上下文压缩（已实现，Mock 验收通过）

按用户选择采用「大工具结果持久化 → 旧工具结果裁剪 → 全量压缩」，不增加按消息数量丢弃中间历史的 History Snip。参考教程的机制分类，不把教学实现描述为 Claude Code 的稳定内部实现。[参考源码](https://github.com/shareAI-lab/learn-claude-code/blob/main/s08_context_compact/code.py)

完整事件与模型输入分开：`agent_run.messages`、模型调用和工具回执保留原文，压缩只改变发送给模型的投影。用户指令、系统约束与未完成工具调用不能被位置裁剪。全量摘要必须读取完整原始历史，包括之前已外置、已裁剪的工具正文，不能对裁剪后的预览再做摘要。

1. 大工具结果完整保存在现有 PostgreSQL 工具回执中，模型只接收有界预览、原始大小、哈希和引用。提供绑定当前运行的分页读取工具，回取原始内容不重新执行业务操作。单项与同批结果分别设预算。
2. 仍超过触发预算时，仅替换已经被模型消费的旧工具结果正文，保留工具名称、call_id、结果状态、关键句柄与回取引用。保留近期结果与当前尚未消费的整批结果；不移除用户消息、助手消息或工具调用 / 回执配对。
3. 仍超预算时，对完整原始历史生成可恢复的任务摘要。完整来源过大时分块顺序摘要，所有块均有记录，不静默截断摘要输入。模型语义摘要之外，固定保留当前要求、作用域、已加载 Skill 版本、工具错误、业务产物引用与权威任务状态。摘要提交成功后才替换已闭合的旧交互前缀，近期完整交互和当前要求继续保留。

压缩检查点、来源哈希、覆盖范围、摘要模型调用与 usage 均持久化。中断恢复复用已完成检查点，真实摘要请求丢失仍标 UNKNOWN，不自动重发。摘要失败不覆盖完整历史；压缩后仍超硬预算明确失败，不靠删除当前要求或破坏工具协议继续。字节预算是工程阈值，不冒充供应商 token 用量。

页面与对话、主与子运行共用压缩器与作用域校验。回取工具只访问当前运行；主 Agent 不能通过引用读取子 Agent 的原文或中间产物。运行视图提供三层触发次数及前后输入大小，完整事实仍由原有业务服务判定。

### 实现与预算

`AgentContextManager` 负责阈值、持久化与检查点，`ContextProjection` 只生成模型输入副本，`AgentRuntime` 继续使用完整记录识别待执行工具和保存新事件。V22 增加压缩事件、摘要检查点、分块模型调用与 usage 记录，并保存工具结果的原始序列化文本，保证分页回读的 SHA-256 与外置引用一致。

主运行创建时纳入同一作用域的全部可见历史轮次，移除此前只取最近四轮的限制；以前主运行自己的原始工具与助手记录以引用存档，摘要时全部读取。历史 MAIN 存档只读取本会话、同一项目或分集，不拼入 SCRIPT / STORYBOARD 的原文。当前明确要求始终原样保留，系统约束不进入可替换区。

| 配置（`vibestory.agent-context`） | 默认值 | 行为 |
| --- | ---: | --- |
| `tool-result-bytes` / `tool-batch-bytes` | 16 / 64 KiB | 单项过大或当前批次累计过大时外置；只在引用比原文小时替换 |
| `preview-bytes` | 1.5 KiB | 外置正文的 UTF-8 安全预览 |
| `trigger-bytes` / `target-bytes` | 256 / 192 KiB | 达到触发值后尝试下一层，旧工具正文裁剪以目标值为停止条件 |
| `keep-recent-results` / `keep-recent-groups` | 3 / 2 | 保留近期已消费结果、近期完整交互组；当前尚未消费的整批回执均保留 |
| `summary-input-bytes` / `summary-output-bytes` | 64 / 8 KiB | 原始存档连续分块的大小，以及单份结构化摘要上限 |
| `max-summary-calls` | 32 | 每个运行的摘要分块调用上限，达到上限明确结束并保留原文 |

配置可通过对应 `AGENT_CONTEXT_*` 环境变量覆盖，运行创建时冻结。主调用原有的 512 KiB 硬限制、16 轮模型 / 24 次工具限制继续生效；摘要调用单独计数并记录 usage。分块中还会携带上块末尾的有限重叠文本，降低一个决定恰好被边界拆开的风险。摘要器没有业务工具权限，输出必须通过 JSON 结构和大小校验。

完整消息不会按数量裁掉。第三层只在工具调用与结果已闭合的边界，把旧前缀替换为摘要与可回读的存档引用；它仍是有损语义摘要，不能承诺保留所有细节。错误、已完成工具与产物句柄、作用域、输入版本、Skill 版本由服务端另外固定保留，不能由摘要改写。若受保护内容仍超过硬预算，运行明确失败。

所有角色可用 `read_tool_result(callId, offset, limit)` 和 `read_history(through, offset, limit)`。分页按 Unicode 码点计数，单页最多 8,192 字符 / 32 KiB，只读取当前运行。外置不重新执行业务工具；已读取的分页结果不会再次被第一层外置。用户可通过 `/api/agent/runs/{id}/tool-results/{callId}` 与 `/history` 查看有权限的原始分页存档，普通执行视图仍只返回有界轨迹。页面在发生完整压缩后显示次数，刷新后仍从同一运行记录恢复。

## Skill 目录作为事实源（已实现，Mock 验收通过）

取消 Java 中的 Skill 名单与 classpath 正文。仓库根 `skills/<name>/SKILL.md` 为内置文件资产，文件以 YAML frontmatter 声明 name、description、roles，正文为操作规范。目录扫描发现新增项，编辑文件后新运行立即读取，无需重新编译。`SKILLS_ROOT` 可指定绝对根目录，API / Worker 必须共享同一路径。

个人新增或修改写入同一根下的 `users/<userId>/<name>/SKILL.md`，同名时作为该用户的覆盖版本。人可直接编辑这些文件，程序通过 Skill API、主 Agent 通过 list_skills / read_skill / save_skill 操作同一文件仓库。内置文件由本机维护者编辑；应用内修改内置项会保存个人覆盖，不影响其他用户。没有数据库中的第二份可编辑 Skill 正文。

每个运行启动时冻结可见目录的元数据、正文与内容哈希。load_skill 只读该运行快照，目录后续修改不影响已开始的运行；数据库保存的是运行证据，不是 Skill 的编辑源。保存接口校验 expectedVersion，写入采用原子替换。目录名与 frontmatter name 一致，拒绝越界路径、符号链接和非法角色。Skill 内容不能扩大服务端工具权限，子 Agent 没有 Skill 写工具。

实现由 `SkillDirectory` 直接扫描文件，`/api/skills` 提供列表、读取与保存，主 Agent 使用同一目录服务。文件格式与操作方式见 [skills/README.md](../skills/README.md)。站内 `/` 菜单仍是业务操作快捷入口，与文件库目录分别提供契约。

验收包括动态新增发现、文件直接编辑、API / Agent 保存后的同文件可见性、个人覆盖隔离、版本冲突，以及编辑后旧运行继续加载旧快照。保持此前三层工作流全 Mock 回归。

本轮新增 V21 保存运行 Skill 快照。`SkillDirectoryTest` 与 `SkillDirectoryIntegrationTest` 共 6 项专项通过：编辑器新增文件后自动发现；程序保存与直接编辑读取同一文件；个人覆盖不影响其他用户；拒绝过期保存、路径越界、符号链接与非法元数据；运行创建后编辑文件仍加载旧正文；主 Agent 创建个人 Skill 后，新的子运行实际通过 load_skill 加载该 ID，无需 Java 注册。

JDK 21、独立 PostgreSQL 16 上的全 Mock 验收通过：168 项后端、17 项组件、15 项 Chrome，无失败、跳过或 flaky。OpenAPI / 类型生成、前端构建与 HTTP 崩溃恢复通过，没有调用真实供应商。[本轮验收记录](../data/verification/phase6-a3ec697b9f/summary.json)

## 三层执行基座补齐（已实现，Mock 验收通过）

此前已经实现独立主子 Session、角色提示词、产物引用和页面 / 对话共享服务，但主会话是代码路由，创作子步骤是一轮模型生成。该实现不等同于能够选择工具并依据结果继续执行的主子 Agent。本轮补齐以下三层，沿用现有权限、任务、版本和来源规则。

| 层 | 职责与执行边界 |
| --- | --- |
| 主 / 子 Agent | 主 Agent 读取服务端阶段摘要，按需加载 Skill、执行明确业务动作或派发 SCRIPT / STORYBOARD 子 Agent。子 Agent 在独立会话内加载 Skill、读取自己的输入与上版产物、提交结构化草稿，依据工具返回的校验问题继续修复。主 Agent 只收到状态、摘要和引用。 |
| 业务 Skill | 以版本化 Markdown 资源声明职责、操作顺序、交付与失败处理，按角色限定可见目录。主、子运行通过同一个 load_skill 工具按需加载。Skill 不授予业务权限，不能绕过工具白名单与版本校验。 |
| 服务端工具 | 提供状态查询、受控业务动作、子任务派发 / 结果读取，以及子会话输入读取和产物提交。固定分集规划继续由服务端窗口任务执行；媒体生成继续走现有持久化 Worker。 |

执行协议使用实际 function calling：assistant tool_calls → 服务端工具结果 → 下一次模型请求，直到产物提交或最终答复。每次模型请求、工具调用及结果持久化，按运行顺序重建上下文。模型调用在事务外，数据库业务工具的写入与对应回执在同一事务内完成；恢复时复用已保存的结果。Skill 文件保存与数据库不构成跨资源事务，通过原子替换和相同正文重放处理中断，若文件又被其他编辑改变则返回版本冲突。主会话逐条串行，子会话同一时刻只允许一个活跃轮次。每次运行限制模型轮数、工具次数与响应大小，越限明确结束；供应商请求结果丢失保留 UNKNOWN，不自动重发真实请求。

页面明确选择的创作动作直接创建对应运行；对话由主 Agent 选择同一工具或派发同一子运行。页面与对话共用 Skill 注册、工具执行、子 Session、产物与版本校验。保留已有明确命令与提案确认行为，并让它们进入共同的工具执行层。普通“继续”不额外授予媒体生成或草案采纳权限。长原文和子草稿不进入主 Agent 模型上下文。

本轮不新增人物规划、审图或审片产品功能，不为生图、生视频分别创建决策 Agent。参考 ArcReel 的职责划分与草稿修复协议，复用已有业务操作。本轮只使用 Mock，不调用真实文本、图片或视频供应商。

验收必须覆盖：主 Agent 按需加载 Skill 后直接执行 / 委派两条路径；子 Agent 读输入、多次工具调用、无效草稿收到问题后修复成功；工具拒绝越权角色、跨集引用、旧版本应用；页面发起、对话接续与反向接续；运行与工具回执刷新 / 中断恢复、重复提交不重复写入；有界循环终止和 UNKNOWN 状态。检查实际工具轨迹，不以 Session ID 或固定答复证明 Agent 能力。全量使用 scripts/verify-all-mock.sh，在独立 PostgreSQL 数据库执行。

### 本轮落地的执行协议

- `SkillDirectory` 扫描根目录中的 SKILL.md，默认提供 workflow、workbench、script、storyboard，支持无需改 Java 新增文件夹。运行冻结完整正文、元数据和 SHA-256，load_skill 读取本轮快照，文件修改只影响后续运行。
- `AgentRuntime` 与 `AgentLoopModel` 执行 function-calling 协议。MAIN 可用 load_skill、get_status、execute_action、delegate_child、await_child，以及 Skill 目录的 list_skills、read_skill、save_skill；SCRIPT / STORYBOARD 可用 load_skill、read_input、read_previous、submit_draft。目录编辑须来自用户明确要求。工具按运行绑定用户、项目和集，不接受模型覆盖身份，也不允许子 Agent 派发子 Agent 或提交媒体。
- 主 Agent 可连续完成“整理剧本，然后规划分镜”：派发后 await_child 挂起运行，Worker 完成子任务后由主运行读取摘要继续派发。单一专业任务也可以先交付子任务引用，用户从页面查看与继续。
- 页面“整理本集剧本”“规划本集分镜”仍直接登记已有创作任务，由同一运行器执行子会话工具循环。页面确认 / 应用与对话 execute_action 最终调用相同事务服务。用户仍须显式审阅、确认、应用，运行完成不等于自动采纳或媒体生成完成。
- V20 新增 agent_run、agent_model_call、agent_tool_call。对话消息与主运行在首次模型请求前一起提交。工具业务写入与回执同事务，模型以不同 call_id 重复同一写操作时仍使用稳定业务请求键。刷新和 Mock 租约恢复复用消息与工具结果；真实请求丢失结果标 UNKNOWN，不能自动重发。
- 每轮运行最多 16 次模型请求、24 次工具调用，每次模型请求序列化后不超过 512 KiB，每份响应不超过 1 MiB。工具错误写成结构化结果参与下一次请求，校验通过才保存创作产物，越限失败且不发布草稿。
- `/api/agent/runs/{id}` 只向拥有权限的用户返回状态、轮数和有界工具摘要，不返回模型输入或子产物正文。页面创作面板与对话展示同一执行记录，完整创作产物仍经原有独立审阅接口加载。

本轮覆盖个人项目的主 / 子运行和现有业务动作，不新增审图 / 审片。共享 Redis 文本准入开启时仍暂停新增创作模型运行，防止绕开现有准入协议。HTTP 文本适配器支持工具协议，本轮验证使用模型 Mock 与真实 PostgreSQL，没有调用真实供应商；Mock 证明控制流、校验和恢复，不证明创作质量。

## 交付范围

页面和 Agent 对话共用分集的生成状态和执行入口。用户可以在对话里发起拆镜，在分镜页确认并提交出图，再回到对话接续；也可以从页面开始，由 Agent 读取本集已经有的镜头、图片和任务。脚本、分镜、视频三个工作区继续承载编辑与预览。

本阶段按以下默认规则开发。主工作上下文按分集 ID 定位，对话历史可以有多条。每条「拆镜后出图」指令保留自己的授权和运行记录。页面已提交的分集任务通过持久化句柄恢复。个人项目支持两种入口，团队项目继续由页面和现有团队权限推进。单独保存正文、修改镜头和方案采纳仍使用各自的版本化业务操作，保存后进入下一次上下文装配。

## 首版的主 Agent 与子步骤

| 角色 | 获取的上下文 | 交回的结果 |
| --- | --- | --- |
| 主 Agent / 编排 Skill | 当前项目和集、阶段摘要、阻塞原因、可执行动作、选中的运行 | 指定动作，或说明待确认事项与可接续动作 |
| 剧本步骤 | 本集正文版本和拆镜任务输入，正文按任务提供给文本模型 | 拆镜任务 ID、镜头集合、确认状态 |
| 分镜步骤 | 本集镜头范围、镜头确认状态、缺图项，出图时由领域服务冻结提示词和资产来源 | 确认结果、图片任务或批次 ID |
| 视频步骤 | 本集目标镜头、已选首帧，提交时由领域服务冻结首帧与视频输入 | 视频任务或批次 ID |

子步骤采用应用内的受控工具和现有 Worker。剧本拆解复用文本适配器，确认、提交和查询使用确定性工具。子步骤的持久化恢复依据为原任务、批次和运行关联。主 Agent 的上下文只含阶段摘要、计数、阻塞和句柄，正文、生成提示词和媒体由相应步骤按需获取。

## 执行与恢复

- 新增按集读取的工作流视图，从正文版本、镜头状态、普通分镜图、选中首帧和任务事实推导建议动作。页面与 Agent 面板展示同一份视图。
- 页面点击提供明确动作和参数。对话中「继续」先定位本会话已授权的运行，或读取当前集建议。服务端通过相同的拆镜、确认、出图、选帧和视频动作调用已有事务服务。
- 有已授权的「拆镜后出图」运行时，页面提交的普通出图批次可关联到同一运行。绑定前核对正文版本、拆镜镜头 ID 集合和镜头确认状态。批次必须在该范围内且与已关联批次成员不重叠。已关联的成员由原批次结算，继续时只提交其余缺图镜头。已关联的失败按原任务恢复。
- 初次拆镜、覆盖重拆、镜头确认、主动重生和未知结果仍依原入口规则执行。对话中明确要求给已选首帧且缺视频的镜头生成视频时，只提交本集满足条件的镜头。单独说「继续」时，视频阶段只报告状态和建议，由用户明确发起视频生成。
- 业务状态、版本与输入快照继续由 PostgreSQL 和已有任务服务负责。沿用请求幂等、批次成员范围校验与项目锁。已生成图片和视频保留各自的提交来源。

## 主子 Agent 扩展规格

### 分集前后的会话边界

整部原文先登记为项目级来源，固定分集规划任务读取来源引用、版本和用户要求，按窗口处理长稿并保存草案，每集包含标题、梗概和对应原文范围。该任务保留 PLAN 会话作为持久化范围，不运行通用子 Agent 工具循环。上层只接收有界摘要、草案 ID 和待确认项。页面可直接打开草案核对原文首尾。用户确认后创建分集并绑定来源版本与范围。用户自带分集时可直接进入单集创作。

每集首次打开主会话或派发创作子步骤时创建一个稳定的主 Session。同一集的多个创作目标各自记录运行。剧本子 Agent 处理本集切片，交回脚本版本引用。分镜子 Agent 读取该版本与相关角色、场景信息，交回分镜方案、版本引用和待审项。两个子 Agent 各自持久化工具调用、修订指令与结构化结果，可按原输入版本继续。主 Agent 用摘要、引用和服务端计划推进下一步。项目级分集运行只规划和建集，各集分别推进下游创作。

[ArcReel 的分集工具与单集脚本规划](https://github.com/ArcReel/ArcReel/blob/110ad6b8c49afbee2782c4e92051e07d434f772a/agent_runtime_profile/.claude/skills/video-workflow/SKILL.drama.md#L74)

### 媒体生成边界

需要根据剧情和用户反馈修订镜头、提示词或生成方案时，由分镜子 Agent 处理。镜头和首帧确认后的图片、视频提交由业务 Skill 调用现有任务服务。Worker 负责执行、状态查询和恢复，主 Session 以任务、批次和媒体版本引用追踪结果。页面和对话共用动作契约、确认和版本校验。若后续引入能根据候选内容提出重做建议的审图或审片，再评估独立的评审子 Agent。

ArcReel 让同一个 `generate-assets` 子智能体执行多种生成工具并汇报结果。VibeStory 的类型化业务工具和持久化任务已有对应的执行与恢复能力。 [ArcReel 的资产生成角色](https://github.com/ArcReel/ArcReel/blob/110ad6b8c49afbee2782c4e92051e07d434f772a/agent_runtime_profile/.claude/agents/generate-assets.md)

### Mock 验收与 token 对照

冻结一份长稿、同一组用户指令与修订、相同的 Mock 工具结果和验收产物。对照单会话携带原文和产物正文的实现，以及主子会话按引用交接的实现。用同一固定 tokenizer 统计序列化后的模型输入，包含系统提示、工具定义、历史和交接摘要。分别报告主 Agent 的峰值输入、主会话累计输入和全链路累计输入，后者纳入子 Agent 调用。记录这是一组固定任务的离线估算，供应商用量和创作质量需要另行验证。

验收覆盖子会话隔离与刷新恢复、页面和对话交替提交，以及原文或脚本版本变化时阻止旧提案覆盖当前产物。本轮纳入整部长稿上传、草案审阅与确认建集，随后可选择一集运行剧本与分镜子 Agent。

### 实现契约

- 项目概览上传 UTF-8 的 TXT 或 Markdown，保存不可变来源。分集规划使用编号段落窗口，模型返回窗口内切点，服务端验证顺序与覆盖并计算 UTF-16 原文偏移。每个完成窗口落库，审阅时展示原文首尾。确认只采用当前来源的草案，按序追加分集，保留已有分集。
- 分集主 Session 对每集唯一，剧本与分镜各有稳定子 Session。子会话轮次记录任务状态、修订要求、输入版本和产物。显式规划分镜时选定剧本产物作为输入。分镜草案首次应用前检查原文版本、镜头版本和脚本引用；已有镜头的覆盖沿用原重拆入口。
- 项目概览与单集故事页提供提交、查看和确认入口。Agent 对话用同一服务发起或接续动作。主会话只读取受限摘要、状态和引用，完整产物由独立审阅接口按需加载。图片和视频沿用已有页面与 Agent 工具。
- 模型调用在事务外由 Worker 执行。每次只领取一个有界窗口，以租约标识保护写回。Mock 可在租约过期后重领；真实文本调用丢失结果时保留未知状态，由用户显式提交新轮次。首版在启用共享 Redis 文本准入时暂停新增创作模型轮次，直到接入同一准入协议。
